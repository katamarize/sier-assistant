## この記事の技術的な核は「状態をプロセスの外に置く」

タスクスケジューラもRotatingFileHandlerも手段にすぎません。本題は、**プログラムが覚えておくべきことを、プログラム自身ではなくSQLiteに持たせた**ことです。

これが決まると、プロセスは「いつ死んでもいい部品」になります。死んでいいなら生死を監視しなくていい。監視しなくていいなら、起動だけOSに任せれば運用が終わる。Step 5でやったのは、この連鎖を最後まで引ききることでした。

聞かれそうなのは「cronやデーモンを使わない理由」「二重実行して大丈夫なのか」あたりです。

## 1. なぜデーモンにしないのか ★最重要

### 1-1. 「デーモン」方式だと何を背負うか

**デーモン(常駐プロセス)** は、プログラムをずっと起動しっぱなしにしておき、そのプログラム自身が時計を見て「8時になったから実行」と判断する方式です。Pythonなら `schedule` や `APScheduler` を使う形になります。

一見シンプルですが、この方式を選んだ瞬間に、これだけの仕事が付いてきます。

| 背負うもの | 中身 |
|---|---|
| 生死監視 | プロセスが落ちていないか誰が確認するのか |
| 自動再起動 | 落ちたとき誰が起こすのか |
| メモリリーク対策 | 何日も動き続けるとメモリが少しずつ増える問題 |
| PC再起動後の復帰 | Windows再起動のたびに手で起動し直すのか |

個人のWindows PCでこれを全部用意するのは割に合いません。しかも**これらは「ニュースを集める」という本来の目的とは無関係な仕事**です。

### 1-2. 使い捨て方式が成立する条件

代わりに選んだのは、**タスクスケジューラが時刻になったらプロセスを起動し、数分で終了して消える**方式です。実行と実行の間、このプログラムはメモリ上のどこにも存在しません。

これが成立するのは、**実行間で引き継ぐべき情報がすべてSQLiteにあるから**です。「どの記事を既に見たか」は `seen_items` テーブル、「どこまで処理したか」は `items.status` にあります。プロセスのメモリには、その実行中の一時的な作業データしか載っていません。

この性質を **ステートレス**(状態を持たない)と呼びます。

具体的に言うと、このパイプラインが引き継ぐ情報は `data/assistant.db` という1つのSQLiteファイルに全部入っています。`seen_items` に既読キーが、`items.status` に処理段階が入っている。プロセスを何度殺しても、このファイルさえ残っていれば続きから動きます。Webアプリでサーバーを何台にも増やせるのも同じ理屈です。

逆に言うと、**Step 2でSQLiteに状態を逃がした時点で、Step 5の設計は決まっていました**。ここは順番が大事で、状態をメモリに持つ作りのままStep 5に来ていたら、デーモン方式を選ばざるを得なかったはずです。

## 2. 二重実行が無害だった理由 — 冪等性の正体 ★

記事に書いた事故(実行中にrun.batを書き換えたら2回走った)で、実際のログはこうでした。

```
01:15:57 正常終了   ← 1回目。12分34秒かかっている
01:15:59 開始       ← 2回目が勝手に始まる
01:16:01 正常終了   ← 1秒あまりで終わる
```

同じコマンドなのに12分34秒と1秒あまり。この差が **冪等性**(べきとうせい / idempotent = 何回実行しても結果が同じ)の正体です。

### 2-1. 分かれ目は「何を処理対象に選ぶか」

冪等になるかどうかは、処理対象の選び方だけで決まります。

```python
# 今の実装: 状態で選ぶ → 冪等になる
pending_items = storage.fetch_pending_items()   # status = 'pending' の行

# もしこうだったら: 日付で選ぶ → 冪等にならない
today_items = storage.fetch_items_by_date(today)  # 今日取得した行
```

上は、1回目が `pending → analyzed` に更新した時点で、2回目には拾うものが残っていません。だから1秒あまりで終わります。

下だと、2回目も同じ記事を拾ってしまい、LLM分析をやり直して通知も2回飛びます。

つまり **`status` は「これから処理すべきものの目印」として働いています**。処理が終わったら目印を外す。この一手間があるだけで、再実行が安全になります。

実務での価値はここです。バッチ処理は必ずいつか失敗します。失敗したとき「途中まで進んだ状態からどう再開するか」を考えなくてよく、**同じコマンドをもう一度叩くだけでいい**。これは運用の負担が段違いに軽くなります。

## 3. logging の3層構造 — printから卒業する ★初学者向け

### 3-1. Logger / Handler / Formatter

`logging` は最初とっつきにくいのですが、役割が3つに分かれているとわかると整理できます。

| 層 | 役割 | たとえるなら |
|---|---|---|
| Logger | ログを受け付ける窓口。名前で区別する | 受付 |
| Handler | 受け取ったログを**どこへ**出すか | 配達員 |
| Formatter | **どんな形**で書くか(日時・レベル・本文) | 書式テンプレート |

[log.py](../src/core/log.py) では、Logger 1つに Handler 2つ(ファイルとコンソール)を付けています。1回 `logger.info(...)` と書けば、2つのHandlerが両方に配ってくれる。だからタスクスケジューラ実行でも手動実行でも、コード側は同じ書き方のままで済みます。

**ログレベル**は重要度の区分です。下から `DEBUG < INFO < WARNING < ERROR < CRITICAL` で、`logger.setLevel(logging.INFO)` と書くと INFO 以上だけが出ます。開発中の細かい出力を `DEBUG` にしておけば、本番では自動的に黙る、という使い分けができます。

### 3-2. なぜ print ではだめなのか

3つあります。

1. **出力先を選べない**。printは標準出力に固定されます。タスクスケジューラ実行では画面がないので、その出力は誰にも届きません
2. **時刻が付かない**。記事の追記(7/18の謎)は、`22:19` という時刻があったから「電源が落ちていた」と分かりました。時刻のないログでは解けません
3. **重要度の区別がない**。全部が同じ見た目だと、`grep WARNING` のような絞り込みができません

実際、今のログは INFO が4468行、WARNING が1971行あります。この規模になると、レベルで絞れないと読めません。

### 3-3. `if logger.handlers: return logger` は何を防いでいるか

```python
def setup(name: str = "assistant") -> logging.Logger:
    logger = logging.getLogger(name)
    if logger.handlers:  # 二重初期化防止
        return logger
```

`logging.getLogger("assistant")` は、**同じ名前なら毎回同じLoggerオブジェクトを返します**(グローバルに使い回される)。なので `setup()` を2回呼ぶと、同じLoggerにHandlerが2セット付いてしまいます。

そうなると1回の `logger.info()` が2行出ます。3回呼べば3行。地味に厄介なのは、これがエラーにならず「なんかログが重複してる」という形でしか気づけないことです。この2行のガードはそれを防いでいます。

## 4. RotatingFileHandler — 放置してもディスクが埋まらない

```python
RotatingFileHandler(LOG_DIR / f"{name}.log", maxBytes=1_000_000, backupCount=5, encoding="utf-8")
```

- `maxBytes=1_000_000`: 1MBを超えたら `assistant.log` を `assistant.log.1` に改名し、新しい `assistant.log` を作る
- `backupCount=5`: 古いものは `.1` 〜 `.5` まで残し、6個目が生まれるときに最古を捨てる

つまり**ログの総量は 1MB × 6 ≒ 6MB で頭打ち**になります。毎日2回、何年も動かす前提なので、上限がないと年単位でGB級になりかねません。

ちなみに今の `assistant.log` は945KBで、1MBまであと少しです。近いうちに初めてのローテーションが起きます。

`encoding="utf-8"` を明示しているのは重要で、これを書かないとWindowsでは既定の文字コード(cp932)でファイルが開かれ、ログに含まれる絵文字(📰 など)で `UnicodeEncodeError` が出ます。次の第5節と根は同じ問題です。

## 5. cp932問題 — なぜ日本語コメントが「実行される」のか ★おもしろい

### 5-1. 文字コードとは

文字コードは、**文字を数値(バイト列)に置き換える規則**です。同じ「あ」でも規則が違えば別のバイト列になります。

| 規則 | 「あ」のバイト列 | 日本語1文字の長さ |
|---|---|---|
| UTF-8 | `E3 81 82` | 3バイトが基本 |
| cp932(Shift_JISのWindows版) | `82 A0` | 2バイト |

問題は、**書くときと読むときで規則が食い違う**ときに起きます。エディタはUTF-8で保存し、cmd(コマンドプロンプト)は `.bat` をcp932として読みます。

### 5-2. なぜ「コメントが実行される」ところまで行くのか

UTF-8のバイト列をcp932の表で引き直すと、まず文字が化けます。ここまでは「読めない文字が出る」だけです。

厄介なのは、**文字の区切り位置までずれる**ことです。UTF-8は3バイト、cp932は2バイトが基本なので、読み進むうちにズレが溜まります。その結果、本来1文字の一部だったバイトが、単独のASCII記号として露出することがあります。

そこにcmdが特別扱いする記号 —— `&`(コマンド区切り)、`|`(パイプ)、`>`(リダイレクト)—— が現れると、`rem` で始まる1行がそこで打ち切られ、**残りがコマンドとして実行されます**。記事に書いた `'.yamlが相対パスのため...' is not recognized` はこれです。

なお、どのバイトが引き金だったかまでは特定していません。対策(ASCIIのみにする)が確実だったので、そこは追いませんでした。聞かれたら正直にそう答える。

### 5-3. 対策の選択肢

- **batのコメントはASCIIだけにする** ← 採用。確実でタダ
- `chcp 65001` でcmdをUTF-8に切り替える。ただしbat内の他のコマンドの挙動にも影響するので、個人用途では前者のほうが楽

Pythonスクリプトの `sys.stdout.reconfigure(encoding="utf-8")` も同じ問題への対処です([daily_news.py](../src/pipelines/daily_news.py))。「Windowsは既定がUTF-8ではない」という一点が、いろいろな場所で顔を出します。

## 6. cmdはバッチファイルを逐次読みする ★事故の真因

二重実行の原因はこれです。

**cmdはバッチファイルを最初に全部読み込みません。** 1行実行するたびにファイルを開き直し、「前回どこまで読んだか」というバイト位置から続きを読みます。

なので実行中にファイルを書き換えると、同じバイト位置にまったく別の内容が来ます。cmdはそれに気づかず、ずれた位置から実行を続けます。今回は、ずれた先がたまたま最終行の実行コマンドだったため、パイプラインがもう一度起動しました。

**Pythonでは同じ事故は起きません。** Pythonはスクリプト全体を起動時に読み込んでコンパイルするので、実行中に `.py` を編集しても、走っているプロセスには影響しません(次回起動から反映される)。この違いは知っておくと役に立ちます。

教訓は単純で、**実行中のbatは触らない**。長い処理を回しているときは終わるまで待つ。

## 7. WakeToRun と StartWhenAvailable の違い

名前が似ていますが、守備範囲がまったく違います。

| 設定 | 何をするか | 効かない場面 |
|---|---|---|
| `-WakeToRun` | **スリープ**からPCを起こして実行する | シャットダウン(電源オフ)からは起こせない |
| `-StartWhenAvailable` | 予定時刻を**逃した**とき、次に起動できたタイミングで遅れて実行する | — |

記事の追記(7/18)で実証されたのは、この境界そのものでした。PCの電源が落ちていたので `-WakeToRun` は無力で、8:00も19:00もスキップ。22:19にPCを起動した直後、`-StartWhenAvailable` が遅れた分を発火させ、1回で全部拾いました。

ここで効いてくるのが、**逃した2回分が2回発火するわけではない**ことです。発火は1回だけ。それで足りるのは、処理対象を「statusがpendingかどうか」で選んでいるからです(第2節)。もし「今日の分を通知する」という選び方だったら、逃した回数を数えて辻褄を合わせる処理が要りました。

`-ExecutionTimeLimit (New-TimeSpan -Hours 2)` は、ハングしたプロセスが翌日の実行を塞がないための保険です。ただし2時間という数字に強い根拠はありません(通常は10分程度で終わる)。

## 8. 終了コード — ログを開く前に失敗に気づく

```python
except Exception:
    logger.exception("=== daily_news 異常終了 ===")
    sys.exit(1)
```

**終了コード**は、プログラムが終わるときにOSへ返す数値です。慣例として `0` が成功、それ以外が失敗を意味します。

タスクスケジューラはこれを記録し、タスク一覧の「前回の実行結果」列に表示します。`sys.exit(1)` を書かないと、例外を捕まえてログに書いただけでプログラムは正常終了扱いになり、**タスクスケジューラ上は「成功」に見えてしまいます**。

つまりこの1行は、「ログを開かなくても、タスク一覧を見れば異常が分かる」状態を作るためのものです。`logger.exception` が原因を残す係、`sys.exit(1)` が異常を知らせる係、と役割が分かれています。

## 9. 初学者がつまづきやすいポイント

**カレントディレクトリと相対パス**: プログラムが `logs/assistant.log` のような相対パスを開くとき、基準になるのは「スクリプトの場所」ではなく「プロセスの作業ディレクトリ(カレントディレクトリ)」です。タスクスケジューラは既定で `C:\Windows\System32` から起動することがあるため、そのままだと `System32\logs\` を探して失敗します。`cd /d %~dp0` はこれを防ぐためのものです。

**`%~dp0` の読み方**: `%0` がバッチ自身のパス、`~d` がドライブ(`F:`)、`~p` がそこからのフォルダパス。合わせて「このbatが置いてあるフォルダ」になります。`cd /d` の `/d` はドライブをまたぐ移動を許可するオプションで、これがないと `F:` から `C:` へは移動できません。

**`@echo off`**: batは既定で「実行するコマンドを画面に出してから実行」します。`echo off` でそれを止め、先頭の `@` は「この行自体も表示しない」という意味です。

**「常駐化」という言葉**: この記事では「毎日勝手に動く状態にする」という意味で使っていますが、技術用語としての常駐(レジデント/デーモン)は「プロセスが居座り続ける」ことを指します。今回やったのはむしろ逆なので、記事内でもそう断っています。

**ログレベルの選び方**: 「異常だが処理は続けられる」= WARNING、「処理が続けられない」= ERROR。今回 LLM分析の失敗を WARNING にしているのは、次回リトライされるので致命的ではないからです。

## 10. 記事に書いていない、今の弱点(聞かれたら正直に答える)

**失敗しても誰も教えてくれない**: これが一番大きい弱点です。通知botなのに、**通知の失敗は通知されません**。異常終了してもSlackには何も飛ばないので、気づけるのは自分がタスク一覧かログを見たときだけです。本来はエラー時に別チャンネルへ投げるべきところ。個人用途で許容していますが、業務システムなら真っ先に指摘される点です。

**WARNINGが大量に出ている**: 現在のログにWARNINGが1971行あり、うち1896行が `[pending維持] LLM分析失敗` です。llama-serverを起動し忘れた日の記録で、設計どおりpendingのまま残って壊れてはいません。ただし「失敗が正常運転に埋もれている」状態でもあり、回数を数えて多すぎたら気づく、といった仕組みはありません。

**未実装のソースを毎回スキップしている**: `[skip] 未対応のtype: html` が73回出ています。Step 7で作る予定のHTML監視用ソースを `sources.yaml` に先に書いてあるためです。害はありませんが、毎回WARNINGが出るのは行儀が良くありません。

**タスク登録スクリプトがリポジトリにない**: 記事にPowerShellのコマンドは載せましたが、`scripts/` にファイルとしては置いていません。PCを新しくしたら記事を見ながら手で叩き直すことになります。

**ローテーション後のログは誰も見ない**: `.log.1` 〜 `.log.5` に退避されたログを読む手段を用意していません。過去を追いたくなったらエディタで直接開くしかない。

**2時間という上限に根拠がない**: `-ExecutionTimeLimit` を2時間にしていますが、実測(通常10分弱、最長でも30分程度)から決めた数字ではありません。「たぶん十分だろう」で置いています。
