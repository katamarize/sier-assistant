## この記事の技術的な核は「冪等性」

**同じ処理を何度実行しても結果が同じになる**(冪等・べきとう)状態をどう作るか。RSSの取得もSQLiteも手段にすぎず、本題はこれです。Step 3のクラッシュ耐性も、Step 5の二重実行が無害だった話も、全部ここから派生しています。

質問が来るとしたら「なぜテーブルを2つに分けたのか」「item_keyに何を使うのか」あたりです。

## 1. item_key — 「同じ記事」をどう定義するか ★最重要

RSSは**毎回フィード全体を返します**。AWS What's Newなら毎回100件。差分をくれるわけではないので、「どれが新着か」はこちら側で判断する必要があります。

その判断キーが `item_key` です。[rss.py:20](../src/collectors/rss.py#L20):

```python
item_key = entry.get("id") or entry.get("link")
```

- 第一候補は `id`(RSS/Atomの規格上、記事を一意に識別するための値)
- 無ければ `link`(URL)にフォールバック

フォールバックが必要なのは、RSSの規格が緩く `id` を出さないフィードが普通に存在するからです。「規格にあるから必ずある」と思い込むと、そういうフィードで `None` が主キーに入り、全記事が同一扱いされて壊れます。

ではタイトルや本文ではだめなのか。タイトルは後から修正されることがあり、修正のたびに「新着」と判定されると通知が二重に飛びます。IDやURLは基本的に不変なので、キーとして安定しています。

将来のHTML監視(Step 7)では、そもそもIDという概念がないので本文のハッシュ値を `item_key` にします。「ページの内容が変わった=新しいItem」という定義に切り替わるわけです。ここが `Item` 型を先に固定しておいた効果で、collectorが変わってもパイプライン側は無変更で済みます。

## 2. なぜテーブルを2つに分けたのか ★聞かれやすい

一見すると `items` テーブルだけで足りそうに見えます(statusを見れば既読かわかる)。分けた理由は**役割が違うから**です。

| テーブル | 役割 | 寿命 |
|---|---|---|
| `seen_items` | 「もう見たか」の判定だけ。複合主キーで高速に引く | 永久に残す(消すと再通知される) |
| `items` | 本文・LLM分析結果を持つ本体。処理キューを兼ねる | 将来的に古いものを消せる |

分けないと何が困るのか。「もう見た記事」は永久に覚えておく必要がありますが、記事本文まで永久に持つとDBが肥大化します。分けておけば `items` だけ古いものを削除しても、既読判定は壊れません。

また `seen_items` は `(source_id, item_key)` を**複合主キー**にしているので、SQLiteが自動でインデックスを張ります。100件のフィードに対して100回の存在確認が走るので、ここが遅いと全体が遅くなります。

## 3. 依存の向き(diff.py → storage.py の一方向) ★設計の話

[diff.py](../src/core/diff.py) はたった6行ですが、意図があります。

```python
def filter_new_items(items: list[Item]) -> list[Item]:
    return [item for item in items if not storage.is_seen(item.source_id, item.item_key)]
```

`diff` が `storage` を呼ぶ**一方向**にしています。逆に `storage` が `diff` を呼ぶ形にすると、お互いがお互いをimportする**循環import**になり、Pythonが起動時にエラーを出します。

`content_hash` の計算を `storage.mark_seen()` の中でやっているのはそのためです([storage.py:82](../src/core/storage.py#L82))。ハッシュ計算は概念的には「差分検知の仕事」ですが、依存の向きを守るためにstorage側に置いています。

一般則として、「どちらがどちらを知っているべきか」を先に決めておくと循環は起きにくくなります。今回は「差分検知はDBを知っている / DBは差分検知を知らない」と決めました。

## 4. INSERT OR IGNORE — 冪等性の実装

```sql
INSERT OR IGNORE INTO seen_items (...) VALUES (...)
```

主キーが衝突したとき、通常の `INSERT` はエラーで落ちます。`OR IGNORE` は**黙って何もせず成功扱い**にします。

これがあるおかげで、同じ記事を2回 `mark_seen()` してもクラッシュしません。「エラーにしない」ことが、そのまま「何度実行しても壊れない」に繋がっています。Step 5で二重実行が無害だったのも、根っこは同じ発想です。

## 5. 記事に書いていない、コードの弱点(聞かれたら正直に答える)

**`with sqlite3.connect()` は接続を閉じない**: Pythonの `sqlite3` の `with` はトランザクションのcommit/rollbackを担当するだけで、**コネクションのcloseはしません**。有名な罠です。現状は関数を抜けたあとガベージコレクタ任せで閉じられており、実害は出ていませんが、厳密には `conn.close()` を書くか `contextlib.closing` を併用すべきところです。

**接続を毎回張り直している**: `is_seen()` は1件ごとに `_connect()` を呼びます。100件なら100回の接続。SQLiteはファイルベースなので致命的には遅くなりませんが、件数が増えたら「一度だけ接続して全件チェック」に変えるべきです。個人用途で問題が出ていないので放置しています。

**`seen_items` は増え続ける**: 掃除の仕組みがありません。1日数百件でも年単位では数万〜十数万件。SQLiteなら余裕ですが、「永久に増えることを承知で残している」という設計判断であることは意識しておく。

**`content_hash` を計算しているが使っていない**: 記事にも書いたとおり、Step 7のHTML監視で使う前提で先に列を用意しています。「使っていない列がある」のは通常なら設計ミスですが、これは意図的な布石です。

## 6. 初学者がつまづきやすいポイント

**RSSとAtomの違い**: どちらもフィード配信の規格ですが、タグ名が違います(`summary` vs `description`、`published` vs `updated` など)。`feedparser` がこの差を吸収してくれるので、コード側では両方を `or` で拾えば済みます([rss.py:27-28](../src/collectors/rss.py#L27-L28))。

**HTMLタグの除去**: RSSの本文にはHTMLタグが混ざります。そのままLLMに渡すとタグがノイズになるので、正規表現で落としています。ただし正規表現でのHTML除去は厳密には不完全(入れ子や属性内の `>` で壊れる)なので、本格的にやるならBeautifulSoupを使うべきところ。RSSの要約文なら実害がないので割り切っています。

**複合主キー**: `PRIMARY KEY (source_id, item_key)` は「2列の組み合わせで一意」という意味。別ソースがたまたま同じ `item_key` を持っても衝突しません。

**日時をUTCのISO8601文字列で保存**: `datetime.now(timezone.utc).isoformat()`。SQLiteには日時型がないので文字列で保存します。ISO8601形式なら文字列のまま大小比較で時系列ソートができるのが利点。ローカル時刻でなくUTCなのは、夏時間やタイムゾーン跨ぎで壊れないようにするため。

**`status` はキューである**: `items.status` を「単なる状態フラグ」と見ると設計の意図を見落とします。`pending` の記事を拾って処理する = キューから取り出す、という発想です。専用のキューシステム(RedisやRabbitMQ)を使わずSQLiteの1列で済ませているのがこのプロジェクトの肝で、Step 3以降のクラッシュ耐性はすべてここから来ています。
