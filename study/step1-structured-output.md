## この記事の技術的な核は1つだけ

「LLMに**必ずパースできるJSON**を返させる」こと。それ以外(dataclass、プロンプトの外部ファイル化、リトライ)は、その核を実用的に扱うための周辺です。逆に言えば、質問が来るとしたらほぼこの1点に集中します。

## 1. スキーマ強制(制約付き生成)の仕組み ★最重要

ここが一番誤解されやすいところで、「JSONで返して」とプロンプトに書くのとは根本的に別物です。

LLMは文章を「次に来る単語(トークン)は何か」を確率で選びながら1つずつ生成しています。スキーマを指定すると、内部でそのスキーマが**文法(grammar)**に変換され、生成のたびに「今この位置で文法的に許されるトークン」以外の確率を強制的にゼロにします。

```
通常:     次の候補 = [ "確", "{", "はい", "```", ... ] から確率で選ぶ
制約あり: 次の候補 = [ "{" ] しか許されない → 必ず "{" が出る
```

つまり**JSONとして壊れた出力は原理的に生成できません**。プロンプトでのお願いは「守ってくれたらいいな」ですが、こちらは仕組みとして保証されます。

- Ollama時代の書き方: `client.chat(..., format=_RESPONSE_SCHEMA)`(記事のコード)
- 現在の書き方(llama-server + OpenAI互換API): `response_format={"type": "json_schema", ...}`([src/llm/llm_client.py:64](../src/llm/llm_client.py#L64))

記事はOllama時代のコードのままなので、「今は違うのでは?」と聞かれたら「番外編でllama.cppに移行し、OpenAI互換の `response_format` に変わりました」と答えれば正確です。

## 2. なぜ小さいモデルほど大変か、そしてトレードオフ ★コメントで指摘された点

制約は「本来出したかったトークン」を禁止することがあります。ここでモデルサイズが効いてきます。

- **大きいモデル**: 放っておいても自然にJSONらしく書けるので、禁止されるケースが少ない。制約があってもズレが小さい
- **小さいモデル(8B級)**: 出力の確率分布がもともと不確かで、制約によって「本来なら選ばなかった低確率のトークン」に押し込まれる頻度が増える

しかもLLMは**自己回帰的**(1つ前までの自分の出力を前提に次を決める)なので、一度不本意なトークンを選ばされると、そのズレが後続にも波及します。結果として「JSONとしては完璧だが、中身が薄い・不自然」という出力になりやすい。

整理すると、こういう綱引きになります。

| 制約 | 形式の確実性 | 内容の質 |
|---|---|---|
| 強く効かせる | パース失敗ゼロ | 犠牲になりやすい |
| 緩める(JSONモード程度) | パース失敗が出る → リトライ・後処理が必要 | 保たれやすい |

どちらに振っても両方を同時に最大化はできない、というのがコメントの指摘の本質です。

## 3. スキーマのフィールド順序が精度に効く ★自分のコードの気づき

制約付き生成では、フィールドは**スキーマの宣言順に埋まっていきます**(文法を順に構築する都合上ほぼ確定的な挙動)。

[llm_client.py:22-40](../src/llm/llm_client.py#L22-L40) の現状の順序:

```
summary → beginner_note → importance → tags → should_notify → reason
                          ^^^^^^^^^^                          ^^^^^^
                          判断が先                             理由が後
```

つまりモデルは**「なぜそう判断したか」を書く前に「重要度」と「通知すべきか」を確定**させています。`reason` はその結論を正当化する後付けの説明になっているわけです。

一般に、結論だけ出させるより理由・思考過程を先に出させたほうが最終的な答えの精度が上がる(Chain of Thoughtの考え方)とされます。なので `reason` を先頭寄りに置くほうが判断の精度は上がる可能性があります。

**ただし未検証**。Step 6のルーブリック化と合わせて比較するとネタになります。

## 4. その他の設計判断(聞かれたら答えられるレベルで)

**`temperature=0.2`**: 出力のランダムさを決める値(0に近いほど毎回同じ答えになる)。今回は創作でなく分析タスクなので、同じ記事には同じ評価が返ってほしい。ゼロにしないのは、完全な決定論だと稀に同じ失敗ループに陥るため。

**リトライ2回 + 独自例外**: [llm_client.py:58-76](../src/llm/llm_client.py#L58-L76)。`except Exception` で全部拾って2回試し、ダメなら `LLMUnavailableError` に包み直しています。呼び出し側(パイプライン)が「LLM関連の失敗」という1種類だけ知っていればよくなる設計。これがStep 3の「失敗したらpendingのまま残す」に直結します。

**プロンプトを `.md` に外出し**: コードを触らずプロンプトだけ差し替えられる。Step 6のルーブリック化はまさにこのファイルだけの変更で済みます。

**`AnalysisResult(**data)`**: JSONの辞書をdataclassに展開。楽ですが、**スキーマとdataclassの定義が二重管理**になっている弱点があります。片方にフィールドを足してもう片方を忘れると `TypeError: unexpected keyword argument` で落ちます。今回は `required` で全フィールドを必須にしているので事故りにくくしています。

## 5. 初学者がつまづきやすいポイント

**「JSONモード」と「JSON Schema指定」は違う**: 前者は「JSONの形にはなる」だけで、キーの有無や型は保証されません。後者は構造まで保証します。今回使っているのは後者。

**量子化(Q4など)**: モデルの重みを低精度な数値に圧縮してファイルサイズとVRAM使用量を減らす技術。`qwen3:8b` のQ4で約5.2GB。精度は多少落ちますが、8GBのVRAMに載せるには必須。番外編のBSODはこの「ギリギリ載る」構成が引き金でした。

**Windowsのcp932文字化け**: `sys.stdout.reconfigure(encoding="utf-8")` の話。Pythonが悪いのではなく、Windowsのコンソールの既定文字コードがUTF-8でないのが原因。Step 5のbatファイル問題も根は同じです。

**ローカルLLMは「起動していないと動かない」**: llama-serverは手動起動(`qwen-start.bat`)。止まっていてもパイプラインが壊れない設計にしてあるのはこのためです。

## 6. コメントが来たときの受け答えの型

技術コメントは「記事への指摘」と「記事に無い視点の追加」で対応が変わります。

- **指摘型**(ここ間違ってますよ) → 事実確認して、必要なら記事を修正 + 追記で明記
- **視点追加型**(こういう難しさもありますよね) → 記事の欠陥ではないので謝る必要はない。「知らなかった/意識していなかった」と正直に受け、自分のコードに引きつけた具体例を1つ返すと会話が続く

今回のコメント(スキーマ強制のトレードオフ)は後者でした。返信で `reason` のフィールド順序に触れたのは、この「自分のコードに引きつけた具体例」にあたります。
