## この記事について

マイルストーン1の最終ステップです。前回までで「収集→LLM分析→Slack 2レーン通知」のパイプラインが手動実行で動くようになりました。今回はこれを、毎日勝手に動く状態にします。

「常駐化」と呼んでいますが、実際にやったのは逆で、**何も常駐させませんでした**。タスクスケジューラが朝夕にプロセスを起動し、数分で使い捨てる。実行間の記憶はすべてSQLiteが持つ。書いたのはバッチファイル1つとログ設定だけです。

## なぜデーモンにしないか

常時起動のプロセス(デーモン)にすると、「そのプロセスが生きているか」を監視する仕事が新たに発生します。落ちたら再起動する仕組み、メモリリークの心配、PCの再起動後に立ち上げ直す手順。個人のWindows PCでこれを背負うのは割に合いません。

一方このパイプラインは、Step 3以来「どこで死んでもDBのstatusを見て続きから動く」設計になっています。プロセスに寿命を求めないなら、起動だけOSに任せればいい。Windowsにはそのための機構(タスクスケジューラ)が最初から載っています。

## 作ったもの1: ファイルログ

定時実行には画面がありません。今まで `print` で流していた進行状況は、誰にも見えなくなります。そこで `logging` のRotatingFileHandlerで `logs/assistant.log` に書くようにしました。

```python:src/core/log.py(抜粋)
file_handler = RotatingFileHandler(
    LOG_DIR / f"{name}.log", maxBytes=1_000_000, backupCount=5, encoding="utf-8"
)
```

- ローテーション付き(1MB×5世代)なので、放置してもログでディスクが埋まらない
- コンソールにも同じ内容を出す2本立て。手動実行時の見え方は変えない
- `main()` 全体をtry/exceptで包み、想定外の例外も `logger.exception` でスタックトレースごとファイルに残す

パイプライン側の変更は、`print(...)` を `logger.info(...)` に機械的に置き換えただけ。「失敗時にログで原因追跡できる」がこのステップの完了条件の半分なので、地味ですがここが本体です。

## 作ったもの2: run.bat(3行)と、そこでの躓き2つ

```bat
@echo off
cd /d %~dp0
uv run python -m src.pipelines.daily_news
```

`cd /d %~dp0` はバッチ自身のあるフォルダに移動する定型句です。DBやログのパスを相対パスにしているので、タスクスケジューラがどこから起動しても作業ディレクトリをリポジトリ直下に固定する必要があります。

たった3行で2回躓きました。3行ですよ?

**躓き1: 日本語コメントが実行される。** 最初、batに日本語で `rem` コメントを書いていました。すると実行時に `'.yamlが相対パスのため...' is not recognized` という謎のエラーが出ます。batファイルはUTF-8で保存してもcmdがcp932として読むため、日本語がバイト境界のずれで化けて、コメントの一部がコマンドとして実行されていました。batのコメントはASCII限定、が教訓です。

**躓き2: 実行中のbatを書き換えると二重実行される。** 躓き1を直そうと、パイプライン実行中(LLM分析に約12分かかる)にrun.batを上書きしたところ、1回目の完走直後にパイプラインが**もう一度走り出しました**。cmdはバッチファイルを一括ロードせず、バイトオフセットで逐次読みします。実行中にファイルが変わると、続きを新しい内容の同じ位置から読むので、何が実行されるか分かりません。

ただ、この事故には収穫がありました。二重実行された2回目のログがこれです。

```
=== daily_news 開始 ===
AWS What's New (aws-whats-new): 新着 0 件
(中略)
LLM分析対象(pending): 0 件
通知対象: メイン 0 件 / ストック 0 件
=== daily_news 正常終了 ===
```

1回目がstatusを更新し終えているので、2回目は何もすることがなく静かに終わりました。**statusベースのキュー設計は、再実行が冪等**(何度実行しても結果が同じ)です。タスクスケジューラの誤発火や手動実行との重複が起きても二重通知しないことが、狙わずに実証されました。

## 作ったもの3: タスク登録

タスクスケジューラへの登録はGUIでもできますが、再現できるようにPowerShellで残しました。

```powershell
$action = New-ScheduledTaskAction -Execute "F:\...\run.bat" -WorkingDirectory "F:\...\sier-assistant"
$t1 = New-ScheduledTaskTrigger -Daily -At 08:00
$t2 = New-ScheduledTaskTrigger -Daily -At 19:00
$settings = New-ScheduledTaskSettingsSet -WakeToRun -StartWhenAvailable -ExecutionTimeLimit (New-TimeSpan -Hours 2)
Register-ScheduledTask -TaskName "sier-assistant-daily-news" -Action $action -Trigger $t1, $t2 -Settings $settings
```

- 朝8:00と夜19:00の2回。時刻は生活リズムに合わせて決めた(PLAN.mdの未決事項がここで消えた)
- `-WakeToRun`: スリープ中でもPCを起こして実行する
- `-StartWhenAvailable`: 時刻を逃した場合(電源オフ等)、次にPCが使えるようになった時点で実行する
- `-ExecutionTimeLimit`: 2時間で強制終了。ハングしたプロセスが翌日の実行を塞がないように

WakeToRunとStartWhenAvailableは役割が違います。前者は「寝ていたら起こす」、後者は「不在だったら帰宅後にやる」。両方付けることで、確実性の網を二重にしています。

## 完了条件は「2日間、手を触れない」

このステップの完了条件は「2日間手を触れずに通知が届き、失敗時にログで原因追跡できること」です。コードと登録は済みましたが、この条件だけは時間が経たないと検証できません。2日間の観察結果を以下に追記します。

### 追記: 2日間の観察結果 — 想定外の形で設計が実証された

1日目(7/17)は8:00・19:00とも定刻に起動し、収集から通知まで完走。ここまでは想定どおりです。

面白かったのは2日目です。ログを見ると、7/18は8:00にも19:00にも実行記録がなく、22:19に1回だけ走っていました。なんで? と思ったら、PCの電源が切れていたためです。`-WakeToRun` はスリープからPCを起こせますが、**シャットダウンされたPCは起こせません**。定時は2回ともスキップされていました。

それでも通知は漏れませんでした。22:19にPCを起動した直後、`-StartWhenAvailable` が逃した分の実行を発火し、2日目の新着をまとめて収集・分析して、メイン10件+ストック11件を通知。取りこぼしはログ上ゼロでした。「定刻に動かなくても、次に動けるときに動けば結果は同じ」というstatusキュー設計の性質が、電源オフという一番現実的な障害でそのまま機能しました。

「毎朝8時ぴったりに欲しい」なら、PCをシャットダウンではなくスリープ運用にする必要があります。私は「起動したら届く」で十分なので、このままにしました。

## マイルストーン1を振り返って

Step 0から5まで、「毎朝、自分に必要な情報が勝手に届く」ニュースbotの最小構成がそろいました。振り返ると、一番効いた設計判断はStep 3の「LLM失敗時はstatusを更新しない」だったと思います。この1つの決めごとが、BSODクラッシュ(#2.5)、Slack未設定、Webhook失敗、そして今回の二重実行まで、すべての異常系を同じ理屈で無害化してくれました。
