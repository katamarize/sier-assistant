## この記事について

前回はSlack通知を実装し、モック検証まで済ませて「あとはWebhookを設定するだけ」と書きました。この記事は、実際にWebhookを設定して動かした初日に起きたことと、その反省で入れた3つの改善の話です。

結論を先に書くと、**通知機能は「送れること」がゴールではありませんでした**。何を・どこへ・どれだけ送るかを絞り込む設計が本体で、それは実データを見るまで決められませんでした。

## 初回実行: 1メッセージに208件

Webhook URLを `.env` に入れて実行したところ、Slackに届いたのは**208件の記事が詰まった1つの巨大メッセージ**でした。スクロールしてもスクロールしても終わりません。読む気は一瞬で消えました(自分で作っておいてなんですが)。

こうなった理由は3つ重なっています。

1. Step 3のクラッシュ検証などで溜まっていたanalyzedの記事が、初回にまとめて放流された(バックログ問題)
2. 通知閾値が「importance 3以上」だった
3. そしてLLMの重要度評価が、想像以上に3に寄っていた

3つ目が本質でした。DBに残っていた評価398件の分布がこれです。

```
importance 2:  40件
importance 3: 313件 (79%)
importance 4:  45件
importance 5:   0件
```

見事な中央寄せ。プロンプトには「重要度を1〜5で評価して」としか書いていません。基準を与えられていないLLMは、迷ったら真ん中に寄せます。その結果「3以上を通知」は「ほぼ全部通知」と同じ意味になっていました。評価の分布を見ずに閾値だけ決めても意味がない、という当たり前のことを、208件のスクロールで学びました。

## 改善1: 閾値を4に上げる — YAMLを1行変えるだけ

まずは止血です。`sources.yaml` の `defaults.min_importance_to_notify` を3から4に変更しました。上の分布なら通知対象は45件/398件、日次では数件程度になる計算です。

Step 3で「閾値はコードでなくYAMLに置く」と決めていたおかげで、この対応はコード変更ゼロ・1行の編集で終わりました。設定の外出しが効くのは、まさにこういう「運用してみたら数字が違った」ときなんですよね。

## 改善2: 捨てずに分ける — 2レーン通知とstatus「stocked」

閾値を上げると、今度は逆の不安が出てきます。importance 3の記事は本当に捨てていいのか? 79%がそこにいる以上、閾値未満=ゴミとは言い切れません。

そこで通知を2レーンに分けました。

```
importance 4以上 → メインチャンネル(朝読む)      → status: notified
importance 3以下 → ストックチャンネル(暇な時に眺める) → status: stocked
```

SlackのIncoming Webhookはチャンネル単位なので、ストック用チャンネルを作ってWebhookをもう1本発行し、`.env` に `SLACK_STOCK_WEBHOOK_URL` として追加しています。未設定の間は従来どおりskippedに落ちる(パイプラインは詰まらない)ようにしました。

statusに `stocked` という値を新設したのは、「メインに通知した」と「ストックに退避した」をDB上で区別するためです。マイルストーン2でNotionへの蓄積を予定していて、そのとき「何をどこに出したか」が追えないと移行できません。

小さな変更に見えますが、statusの値の追加は自分のプロジェクトルールでは**契約(モジュール間の取り決め)の変更**にあたります。PLAN.mdの影響マトリクスで波及範囲を確認し、DESIGN.mdとPLAN.mdの状態遷移の記述を両方更新してからコードを触りました。1人開発でこの手順は大げさに見えるかもしれませんが、「どのチャットのAIに任せても同じ前提で作業できる」状態を保つのが目的なので、ここは省略しません。

## 改善3: 1メッセージ最大10件 — 分割とチャンク単位の確定

208件を1通に詰めた問題そのものへの対策です。重要度の高い順に並べ、10件ずつに分割して送るようにしました。

実装で少し考えたのは、statusをいつ更新するかです。全チャンク送信後にまとめて更新すると、3通中2通送った後の失敗で、送信済みの20件まで次回再送されてしまいます。なので**チャンクを1つ送るたびに、その10件だけstatusを確定**する方式にしました。

```python
for idx, chunk in enumerate(chunks, 1):
    try:
        slack.send(slack.format_message(chunk, header, part), webhook_url)
    except slack.SlackNotifyError:
        return  # 以降のチャンクはanalyzed維持 → 次回再送
    storage.update_items_status([i.id for i in chunk], done_status)
```

「失敗したらDBを更新しない=次回リトライ」という前回からの原則は同じで、その適用単位を全体からチャンクに細かくしただけです。

## 見送った案: 重要度の10段階化

「評価が3に集中するなら、10段階にすれば分解能が上がるのでは?」という案も考えましたが、見送りました。

集中の原因は段階数ではなく、**基準を与えていないこと**だからです。基準がないまま段階だけ増やしても、集中先が3から6〜7に移るだけで、分離したい「通知すべき記事」と「それ以外」は混ざったままです。それに10段階では「6と7の違い」を言葉で定義することもできません。人間が書き分けられない基準を、8Bのローカルモデルが区別できるはずもないんですよね。

本命は5段階のまま、プロンプトに各レベルの定義と具体例を書くルーブリック方式だと考えています。「5=セキュリティ緊急・業務直撃 / 4=主要サービスのGAや大型障害 / 3=知って損はない」のような基準です。とりあえず今回の構成で数日運用して、分布を見てから着手します。

## まとめ

- 通知の設計は実データの分布を見るまで決められない。まず流して、数字を見て、絞る
- 「捨てる」と「今は見ない」を分けると閾値を強気に上げられる。ストックレーンはその受け皿
- 分割送信のstatus確定はチャンク単位に。失敗時の再送範囲が最小になる
- 段階数を増やす前に、基準を言語化する
