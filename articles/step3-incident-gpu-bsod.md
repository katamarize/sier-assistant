## この記事について

Step 3として、[#1](https://zenn.dev/katamarize/articles/step1-ollama-structured-output)で作ったLLM分析と[#2](https://zenn.dev/katamarize/articles/step2-rss-diff-detection)で作ったRSS収集を1本のパイプラインに繋ぐ検証をしていたところ、PCがブルースクリーンで落ちるインシデントに遭遇しました。その顛末をまとめます。

コードの話は少なめ。代わりに「ローカルLLMを実用運用しようとすると、ソフトウェアの設計だけでなくハードウェアの熱管理・メモリ管理まで設計対象に入ってくる」という、開発記としては珍しい気づきの回になりました。

## 何が起きたか

Step 3の検証として、RSS 5ソースから収集済みの pending 記事(100件超)を、Ollama経由でローカルLLM(`qwen3:8b`、Q4量子化で約5.2GB)に連続で流し、重要度判定させるバッチ処理を実行していました。GPUはRTX 3070(VRAM 8GB)で、推論はGPU側にオフロード。

しばらく処理が流れていたのですが、直前のGPUコア温度が89℃まで上がったあたりで、推論の途中に突然画面がブラックアウトしました。PCの電源自体は落ちておらず、ファンは回り続けている。何が起きた?

キーボード叩いてもマウス動かしても相変わらず画面は出ないため、泣く泣くPCを再起動しました。再起動後にイベントビューアーを確認すると、次のログが残っていました。

```
Kernel-Power  Event ID 41  (予期しないシステム再起動/クラッシュ)
EventLog      Event ID 6008 (前回のシステム終了は予期しないものでした)
volmgr        Event ID 162
```

BugCheckコードは `0x133 DPC_WATCHDOG_VIOLATION` (`DPC_QUEUE_EXECUTION_TIMEOUT_EXCEEDED`)。

## WinDbgでの解析

ダンプをWinDbgで開いてスタックを確認すると、`nvlddmkm`(NVIDIAのカーネルモードドライバー)のフレームが複数積まれていました。ここだけ見るとGPUドライバーが直接の犯人に見えます。ただ、同じ解析の中でもう一つ気になる情報が出ていました。

```
Memory manager detected 1 instance(s) of page corruption.
BAD_PAGES_DETECTED: 1
PAGE_NOT_ZERO
```

`nvlddmkm` のフレームは「GPUドライバーがDPC(遅延プロシージャコール)を長時間ブロックした」ことを示しているだけで、それ自体が根本原因とは限りません。むしろページ破損が同時に検出されている以上、まずはメモリサブシステム(RAM/VRAM、あるいはOC設定)起因を疑うのがセオリーです。ドライバーのフレームは、メモリ異常によって二次的にドライバー側の処理が詰まった結果として表面化した「巻き添え」の可能性があります。

## なぜ起きたと考えられるか

原因を断定できるだけの切り分けはまだできていません。ただ、状況証拠を整理すると、次のシナリオが一番筋が通っている気がします。

- GPUコアの温度89℃自体は、RTX 3070のサーマルスロットリング閾値(おおむね93℃前後)には達していない。ただし、コア温度として表示される値と、GDDR6メモリチップ自体の温度(VRAM温度、いわゆるHot Spot寄りの値)は別物で、VRAM側はコア表示より高くなりがち。長時間の連続推論による熱蓄積が、表示上は問題なく見えるコア温度の裏でVRAM側のエラーを誘発していた可能性がある
- `qwen3:8b` はQ4量子化でも約5.2GBあり、VRAM 8GBのカードに対してはKVキャッシュ込みでほぼVRAMを使い切るタイトな構成だった。「VRAMほぼ満載」「高温」「長時間連続推論」という3条件が重なった状態は、メモリ起因の不安定さが最も出やすい条件でもある
- 以上から、「熱蓄積によるVRAM側のメモリエラーが先に起き、それによってドライバー/DPC処理が詰まり `DPC_WATCHDOG_VIOLATION` に至った」という流れは整合的。ただしこれはあくまで状況証拠からの推測で、断定はできない

なお、環境はWindows 11(26100系)、NVIDIAドライバー591.86、CUDA 13.1です。

## 今のところの切り分け手順(実施予定・一部未実施)

根本原因をハードウェアレベルまで確定させるには、本来こういう切り分けが必要だと考えています。現時点ではまだ完了していません。

1. XMP/EXPO(メモリのオーバークロックプロファイル)を無効化した状態で再現するか確認する
2. MemTest86でメインメモリ自体のエラーの有無を確認する
3. DDU(Display Driver Uninstaller)でNVIDIAドライバーを完全にクリーンアンインストールし、必要なら安定版へロールバックして再インストールする
4. HWiNFOでVRAM温度・Hot Spot温度をログしながら、短時間の再現試験を行う

## 助かった点: pendingキュー設計のおかげでデータは無事だった

今回のインシデントで唯一の救いは、`DESIGN.md` の段階で決めていた「LLM分析に失敗した記事は `pending` のまま残す」というキュー設計でした。[前回の記事](https://zenn.dev/katamarize/articles/step2-rss-diff-detection)で触れた `items` テーブルの `status` カラムは `pending → analyzed → notified` と遷移する設計で、クラッシュ時点で分析が終わっていなかった記事は、DBの中に `pending` のまま無傷で残っていました。

収集(RSS取得・既読管理)とLLM分析を明確に分離し、「LLMがどこで落ちても収集済みデータは失わない」前提で設計していたことが、初めての本番相当の連続実行でいきなり効いた形です。再起動後にバッチを再実行すれば、`pending` の記事はそのまま回収できました。障害を前提にした設計、想定していたよりずっと早く報われました。

## 対応: OllamaからGPU圧迫の小さい構成へ

再発防止として、LLM実行基盤をOllamaから `llama.cpp`(`llama-server`)に変更する方向で進めています。狙いはVRAM圧迫を根本的に下げることです。

具体的には、モデルをQwen3系のMoE(Mixture of Experts)モデル(35B MoE、アクティブパラメータ約3B、IQ4_XS量子化)に切り替え（使用したモデルは[こちら](https://huggingface.co/mradermacher/Huihui-Qwen3.6-35B-A3B-Claude-4.7-Opus-abliterated-i1-GGUF/tree/main)）、起動オプション `--n-cpu-moe 28` でエキスパートの大部分をCPU側に配置する構成にしました。MoEはトークンごとに一部のエキスパートしか使わないので、常時GPUに全パラメータを載せておく必要がなく、アクティブに使う部分だけをGPU側に残しつつ、大部分をCPU側にオフロードできます。これでVRAM使用量に余裕を持たせ、今回のような「VRAMほぼ満載+高温+長時間連続推論」という条件そのものを避けたい考えです。

あわせて、運用面でも次の対策を検討しています。

- 1回の実行で処理する `pending` 件数に上限を設ける(長時間の連続GPU負荷を避ける。副次的にSlack通知の「通知疲れ」防止にもなる)
- `nvidia-smi -pl` でGPUの電力上限を下げ、発熱そのものを抑える

## まとめ

今回の一番の学びは、「ローカルLLMを個人PCで実用運用しようとすると、ソフトウェアのキュー設計だけでなく、GPUの熱・VRAMの容量というハードウェア側の制約まで含めて設計しないと、思わぬところでシステムごと落ちる」ということでした。BugCheckのスタックだけを見ればNVIDIAドライバーが疑わしく見えますが、page corruptionという別の兆候が同時に出ている以上、安易にドライバーだけを犯人扱いせず、メモリ・熱という土台から疑うべきだと感じています。

MemTest86などによる根本原因の切り分けはまだ完了しておらず、ハードウェア(メモリ/VRAM)起因の可能性は依然として残ったままです。ここは正直に「未解決」として記録しておき、次回以降の記事で追って報告するつもりです。
